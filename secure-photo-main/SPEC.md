# SPEC: Secure Photo Share

Документ для Claude Code. Читать целиком перед началом работы, реализовывать строго по этапам из раздела 12. Места, в которых автор спецификации не уверен, вынесены в раздел 15: их нужно проверить на практике, а не принимать на веру.

## 0. Правила работы

- Сначала создай структуру репозитория (раздел 11) и `docs/PROTOCOL.md` с копией раздела 5. Протокол шифрования нельзя менять без обновления этого файла.
- Главный технический риск проекта: веб-страница (WebCrypto в Safari) и Android (Keystore + JCA) должны шифровать и расшифровывать байт в байт одинаково. Первым делом напиши и пройди тест совместимости (раздел 13.1), только потом всё остальное.
- Не добавляй сторонние аналитику, крашлоггеры и трекеры. Не логируй содержимое запросов, токены и расшифрованные данные.
- Перед выбором любой библиотеки, версия которой не указана здесь, проверь актуальную версию и совместимость.
- Если нужно решение, которого нет в документе, выбери простейший вариант, запиши его в `docs/DECISIONS.md` и иди дальше.

## 1. Цель

Два человека. Отправитель (iOS) загружает фото через веб-страницу в Safari, ничего не устанавливая. Получатель (Android) смотрит фото в собственном приложении. Получатель может открывать фото многократно в пределах лимита, который задал отправитель, но не может скачать файл, сделать скриншот или запись экрана средствами системы.

Один экземпляр системы обслуживает ровно одну пару. Масштабирование, регистрация пользователей и публичный доступ не нужны.

## 2. Модель угроз

| Угроза | Защита | Статус |
|---|---|---|
| Скриншот и запись экрана на Android | `FLAG_SECURE` | закрыто |
| Трансляция экрана (Cast, Miracast) | `FLAG_SECURE` | закрыто |
| Превью в списке недавних приложений | `FLAG_SECURE`, `setRecentsScreenshotEnabled(false)` | закрыто |
| Сохранение файла в галерею или файловую систему | фото живёт только в памяти, кеш выключен | закрыто |
| Перехват на сервере | сквозное шифрование, сервер видит только шифротекст | закрыто |
| Подмена ключа получателя сервером | публичный ключ передаётся внутри ссылки (фрагмент URL), не через сервер | закрыто |
| Фото экрана на другую камеру | динамический водяной знак | только сдерживание |
| Root, Frida, модифицированный APK с вырезанным `FLAG_SECURE` | Play Integrity (этап 5, необязательно) | частично |
| Получатель, которому нельзя доверять вообще | ничем не закрывается | не решается |

Вывод для реализации: обещать «100% защиту» нельзя. Приложение честно решает задачу «исключить все программные пути сохранения на честном устройстве».

## 4. Стек

- Сервер: Node.js 20+, TypeScript, Fastify, better-sqlite3, хранение файлов на локальном диске. Развёртывание: Docker Compose + Caddy (автоматический HTTPS). Альтернатива по желанию владельца: Cloudflare Workers + R2 + D1.
- Веб-страница отправителя: один статический `index.html` + `app.js`, без сборщика и фреймворков, только стандартный WebCrypto.
- Android: Kotlin, Jetpack Compose, minSdk 31, OkHttp, kotlinx.serialization, `androidx.biometric` (опционально), ZXing core для показа QR.

## 5. Протокол шифрования (нормативная часть)

Схема ECIES-подобная, на примитивах, которые есть и в WebCrypto, и в Android без сторонних библиотек.

Ключи получателя:
- Пара ECDH на кривой P-256 (`secp256r1`), создаётся в Android Keystore, закрытый ключ неизвлекаемый.
- Публичный ключ экспортируется в формате X.509 SubjectPublicKeyInfo (SPKI, то, что возвращает `PublicKey.getEncoded()`) и кодируется base64url без padding.

Шифрование (на стороне отправителя, в браузере):
1. `photo_id` = случайный UUID v4, генерируется в браузере.
2. Импортировать публичный ключ получателя: `crypto.subtle.importKey('spki', ..., {name:'ECDH', namedCurve:'P-256'}, false, [])`.
3. Сгенерировать эфемерную пару ECDH P-256.
4. `shared = ECDH(eph_private, receiver_public)` (32 байта, `deriveBits`, 256 бит).
5. `key = HKDF-SHA256(ikm = shared, salt = 32 нулевых байта, info = UTF-8("securephoto-v1"), length = 32)`.
6. `iv` = 12 случайных байт.
7. `ct = AES-256-GCM(key, iv, plaintext = JPEG-байты, aad = UTF-8(photo_id))`, тег 128 бит дописан в конец шифротекста (стандартное поведение WebCrypto).
8. Полезная нагрузка (то, что уходит на сервер): `eph_public_raw (65 байт: 0x04 || X || Y) || iv (12 байт) || ct`.

Расшифровка (Android):
1. Разобрать нагрузку: первые 65 байт, затем 12, остальное шифротекст.
2. Из 65 байт собрать `ECPublicKey` через `ECPublicKeySpec(ECPoint(x, y), params)`, где `params` взяты из публичного ключа получателя.
3. `KeyAgreement.getInstance("ECDH")`, `init(keystorePrivateKey)`, `doPhase(ephPublic, true)`, `generateSecret()`.
4. HKDF вручную через HMAC-SHA256: `prk = HMAC(key = 32 нулевых байта, data = shared)`, `key = HMAC(key = prk, data = info || 0x01)`. Длина 32 байта, поэтому нужен один блок.
5. `Cipher.getInstance("AES/GCM/NoPadding")`, `GCMParameterSpec(128, iv)`, `updateAAD(photo_id)`, `doFinal(ct)`.

Требования к входным данным браузера: перед шифрованием фото перекодируется через canvas в JPEG, качество 0.85, длинная сторона не более 2048 px. Это заодно убирает EXIF (геометки, модель камеры). Итоговый размер не более 15 МБ.

## 6. Ссылка-приглашение

Формат: `https://<домен>/s/#r=<room_id>&k=<sender_secret>&pk=<pubkey_spki_b64url>`

Всё после `#` браузер не отправляет на сервер, поэтому секреты не попадают в серверные логи. Страница при загрузке читает фрагмент, сохраняет значения в `localStorage` и продолжает работать при перезагрузке. `sender_secret` даёт право только загружать фото; читать, перечислять или удалять чужие фото им нельзя. Получатель может отозвать ссылку (раздел 7, ротация), после чего старый секрет перестаёт работать.

## 7. Серверное API

Общие правила: только HTTPS, HSTS, ответы фото с `Cache-Control: no-store`, CORS разрешён только для origin страницы отправителя, лимиты частоты (например 30 запросов в минуту на IP), лимит тела 16 МБ, заголовок `Authorization` в логи не попадает.

Аутентификация: `Authorization: Bearer <token>`. Токены случайные, 32 байта, в БД хранится SHA-256 хэш.

| Метод и путь | Кто | Что делает |
|---|---|---|
| `POST /api/rooms` | получатель | Тело: `{pubkey}`. Создаёт комнату, возвращает `{room_id, receiver_token, sender_secret}`. Разрешён, только пока число комнат меньше `MAX_ROOMS` (по умолчанию 1), плюс обязателен заголовок `X-Registration-Secret` из переменной окружения. |
| `POST /api/rooms/:id/rotate-sender` | получатель | Выпускает новый `sender_secret`, старый перестаёт работать. |
| `PUT /api/photos/:photo_id` | отправитель | Заголовки: `X-Room-Id`, `X-Max-Views` (0 = без лимита), `X-Ttl-Seconds` (от 60 до 2592000). Тело: `application/octet-stream`, нагрузка из раздела 5. Ответ 201. Повторный PUT с тем же `photo_id` даёт 409. |
| `GET /api/photos` | получатель | Список активных фото: `{id, created_at, size, max_views, views_used, expires_at}`. Без содержимого. |
| `POST /api/photos/:id/open` | получатель | Заголовок `X-Open-Id` (UUID). Атомарно увеличивает `views_used`, отдаёт нагрузку, заголовки `X-Views-Left`, `X-Expires-At`. Повтор с тем же `X-Open-Id` в течение 2 минут не считается новым просмотром (защита от обрыва сети). Если лимит исчерпан или срок вышел, 410. После отдачи последнего разрешённого просмотра файл удаляется. |
| `DELETE /api/photos/:id` | получатель | Немедленное удаление. |
| `GET /healthz` | любой | Проверка живости. |

Фоновая задача раз в минуту удаляет файлы с истёкшим сроком и с исчерпанным лимитом, затем помечает строки в БД.

Ошибки возвращаются как `{error: "<code>"}` без деталей внутренностей.

## 8. Модель данных (SQLite)

```
rooms(
  id TEXT PRIMARY KEY,
  receiver_pubkey TEXT NOT NULL,
  receiver_token_hash TEXT NOT NULL,
  sender_secret_hash TEXT NOT NULL,
  created_at INTEGER NOT NULL
)

photos(
  id TEXT PRIMARY KEY,           -- photo_id из браузера
  room_id TEXT NOT NULL REFERENCES rooms(id),
  blob_path TEXT NOT NULL,
  size INTEGER NOT NULL,
  max_views INTEGER NOT NULL,    -- 0 = без лимита
  views_used INTEGER NOT NULL DEFAULT 0,
  expires_at INTEGER NOT NULL,
  created_at INTEGER NOT NULL,
  deleted_at INTEGER
)

opens(
  open_id TEXT PRIMARY KEY,
  photo_id TEXT NOT NULL,
  created_at INTEGER NOT NULL
)
```

Счётчик просмотров увеличивается одной атомарной транзакцией с проверкой лимита и срока.

## 9. Веб-страница отправителя

Файлы: `web/index.html`, `web/app.js`, `web/manifest.webmanifest` (по желанию), иконка.

Поведение:
1. При загрузке разобрать фрагмент URL, сохранить `r`, `k`, `pk` в `localStorage`. Если данных нет, показать сообщение «Откройте ссылку, которую вам прислали».
2. Выбор фото через `<input type="file" accept="image/*">`.
3. Предпросмотр, выбор лимита просмотров (1, 3, 10, без лимита) и срока жизни (1 час, 24 часа, 7 дней).
4. Кнопка «Отправить»: декодировать через `createImageBitmap(file, {imageOrientation: 'from-image'})`, уменьшить на canvas, получить JPEG, зашифровать по разделу 5, отправить `PUT`. Показать прогресс и итог.
5. Ошибки показывать простым текстом (нет сети, ссылка отозвана, файл слишком большой).

Требования: страница обязана открываться по HTTPS, иначе `crypto.subtle` недоступен. Дизайн простой и крупный, рассчитанный на телефон. Никаких внешних скриптов и шрифтов.

## 10. Android-приложение

Экраны:
1. Онбординг: создать ключ в Keystore (алиас `receiver_ecdh`, `PURPOSE_AGREE_KEY`, `secp256r1`), вызвать `POST /api/rooms`, сохранить `room_id` и `receiver_token` в `EncryptedSharedPreferences` или в шифрованном DataStore. Показать ссылку из раздела 6 с кнопкой «Поделиться» и QR-кодом.
2. Список входящих: карточки с временем, размером, оставшимися просмотрами и сроком. Обновление при открытии и по кнопке.
3. Просмотр: запрос `open`, расшифровка в памяти, показ картинки с водяным знаком, кнопка «Закрыть». Никаких кнопок «поделиться» и «сохранить».
4. Настройки: отозвать ссылку отправителя (ротация), удалить все фото, включить биометрию при открытии просмотра.

Обязательные меры безопасности:
- `window.setFlags(FLAG_SECURE, FLAG_SECURE)` в `MainActivity.onCreate` до `setContent`, на всё приложение.
- `setRecentsScreenshotEnabled(false)`.
- В манифесте `android:allowBackup="false"`, правила `dataExtractionRules`, исключающие всё, отсутствие экспортируемых компонентов кроме launcher-активности, отсутствие `FileProvider`.
- Расшифрованные байты держать только в `ByteArray` и `Bitmap` внутри состояния экрана просмотра. После закрытия экрана, а также в `onStop`, обнулять массив (`fill(0)`), освобождать `Bitmap` (`recycle`), сбрасывать состояние.
- Сетевой слой: отключить `Cache` в OkHttp, не писать тело ответа на диск, в релизе выключить логирование.
- `setHideOverlayWindows(true)` на экране просмотра (защита от наложенных окон).
- Водяной знак: собственный `Canvas`-слой поверх фото, повторяющийся диагональный текст с меткой (например «для <имя получателя>») и текущим временем, обновляется раз в секунду. Рисуется внутри защищённого окна.
- Релизная сборка не `debuggable`.

Биометрия (`BiometricPrompt`) включается опционально. Пуш-уведомления: этап 4, через FCM data-сообщение «есть новое фото» без содержимого; запасной вариант без Google Services: `WorkManager` с периодическим опросом (минимальный интервал 15 минут).

Приложение не кеширует шифротекст локально, так как это позволило бы смотреть фото после удаления на сервере и обходить счётчик просмотров. Каждое открытие идёт на сервер.

## 12. Этапы и критерии приёмки

**Этап 0. Совместимость криптографии.** Скрипт в `tools/interop` (Node 20+, у него есть `globalThis.crypto.subtle`) шифрует тестовый файл зафиксированными ключами, JVM-тест в `android/app/src/test` расшифровывает и сравнивает байты. Приёмка: тест зелёный, формат нагрузки полностью совпадает с разделом 5.

**Этап 1. Сервер.** Все эндпоинты раздела 7, БД, фоновая очистка, тесты API. Приёмка: тесты на лимит просмотров (включая параллельные открытия), срок жизни, идемпотентность `X-Open-Id`, отзыв ссылки, `MAX_ROOMS`.

**Этап 2. Веб-страница.** Раздел 9. Приёмка: с реального iPhone в Safari фото уходит на сервер, на диске лежит только шифротекст (проверить, что файл не открывается как JPEG).

**Этап 3. Android, ядро.** Онбординг, Keystore, список, просмотр, расшифровка, `FLAG_SECURE`, водяной знак. Приёмка: фото с iPhone отображается на Android, чеклист из раздела 13.2 пройден.

**Этап 4. Удобство.** Уведомления, биометрия, ротация ссылки в настройках, обработка ошибок и слабой сети.

**Этап 5. Усиление (необязательно).** Play Integrity API, отказ показывать фото на неподтверждённом устройстве. Требует Google Play Services и проекта в Google Cloud.

**Этап 6. Развёртывание.** `docker compose up` на VPS с доменом, Caddy получает сертификат сам. Приёмка: весь путь работает по реальному домену.

Возможное расширение после MVP: двусторонний чат с текстом, зашифрованным по той же схеме (тогда браузеру понадобится собственная пара ключей в IndexedDB).

## 13. Тестирование

### 13.1 Совместимость
Фиксированные тестовые векторы, шифрование в Node, расшифровка в JVM и обратное направление для проверки самой схемы. Отдельно проверить: пустой AAD и неверный AAD должны давать ошибку расшифровки; порча одного байта шифротекста должна давать ошибку.

### 13.2 Ручной чеклист на Android (релизная сборка)
- скриншот кнопками, результат: система запрещает или снимок чёрный;
- запись экрана, результат: чёрный экран на месте фото;
- список недавних приложений: нет превью содержимого;
- трансляция на внешний экран: чёрный экран на месте фото;
- `adb exec-out screencap`: чёрный кадр;
- `adb shell run-as <package>`: доступ запрещён (не debuggable);
- резервное копирование: данные приложения не попадают в бэкап;
- `logcat`: нет токенов, ключей и содержимого;
- файловая система приложения после просмотра: нет файлов с фото;
- после окончания лимита просмотров: сервер отвечает 410, файл с диска сервера удалён.

### 13.3 Сервер
Нагрузочная проверка гонки открытий (два одновременных `open` на последнем разрешённом просмотре: ровно один получает данные).

## 14. Развёртывание и эксплуатация

- Переменные окружения: `REGISTRATION_SECRET`, `MAX_ROOMS`, `DATA_DIR`, `ALLOWED_ORIGIN`, `PORT`.
- Том Docker для `DATA_DIR`; резервные копии не нужны (данные эфемерные), но БД и файлы должны переживать перезапуск.
- Логи только уровня запросов (метод, путь без секретов, статус), без заголовков.
- Регулярные обновления образа и зависимостей.

## 15. Места, требующие проверки на практике

Автор спецификации не проверял их в бою, уверенность указана приблизительно.

1. Работа `KeyAgreement` ECDH поверх ключа с `PURPOSE_AGREE_KEY` в Android Keystore на устройствах Android 12+ (уверенность высокая, но поведение у отдельных производителей различается). Запасной вариант, если не заработает на устройстве получателя: сгенерировать пару в программном провайдере и хранить закрытый ключ, зашифрованный AES-ключом из Keystore.
2. Сохранение фрагмента URL при добавлении страницы на экран «Домой» в iOS и общее хранилище между Safari и такой иконкой (уверенность низкая, по имеющимся данным хранилище у них раздельное). Если фрагмент теряется, отправителю проще пользоваться страницей в обычной вкладке Safari, а поддержку иконки из MVP исключить.
3. Поведение HEIC при выборе фото на iPhone: Safari обычно сам отдаёт совместимый формат или декодирует HEIC в `createImageBitmap` (уверенность средняя). Проверить на реальном устройстве и при необходимости попросить в интерфейсе выбирать «Наиболее совместимые».
4. Поведение `setHideOverlayWindows` и `setRecentsScreenshotEnabled` зависит от версии Android (API 31 и 33 соответственно); на старых версиях вызов нужно обернуть проверкой `Build.VERSION.SDK_INT`.
